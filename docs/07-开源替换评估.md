## 1. 结论摘要

评估覆盖 `src/agentos` 全部模块（约 13500 行）。当前依赖仅 `fastapi` / `uvicorn` / `pydantic` / `typer` / `httpx` / `mcp` / `jsonschema` / `sqlite-vec` / `pyjwt[crypto]`，缺少数据库层、可观测、调度、认证库的支撑，基础能力基本为自研。

**核心判断：项目的主要风险不是"自研过多"，而是"自研件完成度差异巨大"。**

- `services/workflow.py` 仅 137 行，只实现了持久化执行的皮毛；
- `adapters/store/sqlite.py` 达 2057 行，手写 SQL 承担了连接、迁移、事务与并发；

两者指向相反的处理方式：**轻的整块替换，重的换底层实现但保留语义**。

## 2. 判据：三档分类法

判断一件自研代码是否该换，依次问三个问题：

| 档位 | 判据 | 处理方式 |
| --- | --- | --- |
| **整块替换** | 业界有成熟实现；自研部分无差异化；维护成本高于集成成本 | 删除自研实现，接入开源件，保留 Port 契约 |
| **换底层保留语义** | 自研价值在**语义**（业务规则、状态机、一致性保证），底层是重复劳动 | 保留上层语义与 Port，替换底层库 |
| **保留** | 属于本项目的核心差异化；或规模过小，引入依赖的成本高于自维护 | 不动；记录未来复审条件 |

补充两条否决规则，命中即不换：

- **规模否决**：100 行以内的自研件，引入第三方依赖通常不划算。
- **语义否决**：替换会破坏既有不变量（幂等、审批指纹、不确定态对账、租约）且无法用测试兜底的，先补测试再动。

## 3. 执行循环与编排

### 3.1 现状

| 组件 | 规模 | 说明 |
| --- | --- | --- |
| `runtime/loop.py` | 576 行 | 显式状态机驱动的 ReAct 循环 |
| `runtime/executor.py` | 401 行 | 工具执行的确定性闸门 |
| `services/planning.py` | 463 行 | PlanRunner，执行 TaskPlan DAG |
| `services/workflow.py` | 137 行 | 工作流定义与版本化 |

`loop.py` 已实现的自研能力：checkpoint 持久化、崩溃后重放已持久化的待执行调用、三重护栏（步数 / token / 重复动作）、租约防双跑、不确定态强制暂停对账。

**确认为缺口**：全仓不存在上下文压缩或滚动摘要。`checkpoint["messages"]` 只增不减，触及 token 预算即终止，不做压缩续跑。因此当前循环**抗崩溃强、抗长程语义漂移弱**。

### 3.2 选型依据

**开源范围**：其 CLI 与 Harness 执行框架以 Apache-2.0 开源（Rust 实现），且集成层一并开放，官方提供了面向嵌入式集成的协议文档与 SDK。这使它不只是可替换的执行器，而是**可被产品集成的执行底座**。

集成深度分三层：一次性命令行执行、语言 SDK、长驻进程加双向 JSON-RPC。本文采用第三层。

**决定性差异化：支持自定义模型供应商。** 可通过配置将请求指向任意兼容其接口规范的端点，已验证可用于多家第三方与本地推理服务。这一点直接排除了 Claude Agent SDK 一类候选——其 Python 包虽为 MIT 许可，但绑定自家模型、不支持自定义端点，无法接入私有或第三方模型。

**量化依据**：公开基准显示，在**模型不变**的前提下，保留推理链与上下文压缩两项改造可带来数倍的任务完成率提升，同时输出 token 大幅下降。这说明长任务表现主要由执行框架决定，而非模型本身——这是本次替换的核心理由。

**候选对比**（评估时点）：

| 方案 | 许可 | 关键差别 |
| --- | --- | --- |
| Codex | Apache-2.0 | 支持自定义供应商端点；操作系统级沙箱（macOS 与 Linux 各有实现） |
| OpenCode | MIT | 供应商中立，规划与执行双 agent 结构 |
| OpenHands | MIT | 容器沙箱、可自托管，适合多用户平台形态 |
| Claude Agent SDK | MIT（Python 包） | 绑定自家模型，不支持自定义端点 |
| Gemini CLI | Apache-2.0 | 个人额度已迁移至闭源客户端，是"代码开源"与"使用授权分离"的警示案例 |

三者同时满足的只有 Codex：自定义供应商端点、操作系统级沙箱、上下文压缩内置。

### 3.3 替换建议

| 组件 | 建议方案 | 许可 | 保留边界 |
| --- | --- | --- | --- |
| `loop.py` 执行循环 | Codex app-server 双向 JSON-RPC | Apache-2.0 | 审批、Policy、账本、幂等全部留在 AgentOS 侧 |
| `planning.py` + `workflow.py` | Temporal（Python SDK） | MIT 内核 | 任务与角色的授权仍由 Policy 裁定 |

**两者不冲突，是上下层**：Temporal 负责多步骤编排、DAG 与长事务；Codex 负责单个 agent 的推理循环。可共存形态为 Temporal 编排、每个 activity 内执行一个 Codex turn。不要二选一。

**最大的单项收益**：采用该方案后，上下文压缩由框架提供，§3.1 记录的缺口自动消除，无需自研。

### 3.4 Codex app-server 接入要点

映射关系：

| AgentOS | Codex app-server |
| --- | --- |
| Run | thread（start / resume / fork / rollback） |
| 一次模型调用 | turn（含多个 item，有 started / delta / completed 生命周期） |
| 审批服务 | 服务端主动发起的审批请求 |
| 工具执行 | 动态工具：注册客户端处理器，服务端发起调用请求 |
| 上下文压缩 | 内置压缩接口，无需自研 |

接入方式：Python SDK，或自行实现 stdio JSON-RPC 客户端（协议结构可由 CLI 生成）。

**状态必须分家**：Codex thread 是"对话状态"，AgentOS store 是"治理账本"，用 `thread_id` 外键关联，**不合并**。两者生命周期与一致性要求不同。

**不确定态语义无处安放**：Codex 无对应概念，需保留在动态工具处理器内——执行结果未知时返回特定结构，由 AgentOS 侧将 run 置为暂停。

## 4. 身份与企业认证

### 4.1 现状

| 组件 | 规模 | 说明 |
| --- | --- | --- |
| `kernel/ports.py` 的 IdentityPort | 契约 | 仅两个方法，凭据为无 schema 字典 |
| `services/identity.py` | 23 行 | 只持有单个后端，无注册表、无分派 |
| `adapters/identity/oidc.py` | 118 行 | OIDC JWT 后端，**未接入组合根** |
| `adapters/identity/local_tokens.py` | 286 行 | 本地令牌后端，当前生产路径 |

**关键发现**：`composition.py` 中身份后端为硬装配的单一本地令牌实现，`OIDCJwtIdentity` 仅在测试中被实例化。即：OIDC 支持此前**从未接入生产路径**。

### 4.2 关键结论：IdentityServer4 不需要专门适配器

IdentityServer4 是标准 OIDC 实现。现有 `oidc.py` 无法对接它的原因是其中固化了另一款 IdP 的专有假设，而非缺少协议支持：

| 固化点 | 现状 | 问题 |
| --- | --- | --- |
| 密钥集路径 | 硬编码特定 IdP 的 certs 路径 | 应改为读取 discovery 文档中的 `jwks_uri` |
| 角色声明 | 读取特定嵌套结构 | 不同 IdP 的声明名不同，须可配 |
| 主体声明 | 优先读取专有字段 | 应配置候选列表按顺序取值 |
| 租户来源 | 读取固定 claim 名 | 须可配，且不得由外部覆盖 |
| 签名算法 | 硬编码单一算法 | 应支持算法列表配置 |
| 凭据分派 | 依 token 形态嗅探 | 多家企业均签发 JWT 时会误判，应改为显式匹配 |

将这六处外置为配置后，**单个 OIDC 适配器即可通吃主流 IdP**。

### 4.3 三层抽象

不要按协议拆分，要按动作拆三层：

| 层 | 职责 | 数量 |
| --- | --- | --- |
| Resolver | 按签发方、受众或租户域名选择通道 | 一个 |
| Verifier | 验签 / 验票 | 少数几个，按协议分 |
| ClaimMapper | 声明映射为统一身份上下文 | **每企业一份配置**，这才是主要工作量 |

需要独立 Verifier 的只有：OIDC、裸 JWT（无 discovery，手工配置密钥集）、SAML 2.0、LDAP/AD、API Key 与 mTLS。

配置形态示意（占位符）：

```yaml
identity:
  default_lane: local
  lanes:
    - id: <lane-id>
      match: {issuer: "https://sso.example.com"}
      verifier:
        kind: oidc
        discovery: "https://sso.example.com/.well-known/openid-configuration"
        algorithms: [RS256]
        audience: "agentos-api"
        leeway_s: 30
      mapping:
        subject: ["preferred_username", "sub"]
        tenant: {claim: "org", default: "default"}
        roles:
          source: "role"
          map: {admin: [read, write, approve, admin]}
        unmapped_role: deny
```

新增企业只增加一段配置，不改代码。

### 4.4 替换建议与硬约束

`adapters/identity/oidc.py` → 使用成熟认证库（如 authlib）并实现配置化声明映射，补上现有实现缺失的令牌内省（RFC 7662）。

企业场景必须满足：

1. **租户标识只能来自令牌内部的可信声明**，绝不能取自请求参数或请求头，否则可伪造跨租户访问。
2. **密钥集需支持 kid 轮换、缓存 TTL，不可达时 fail-closed**。现有实现的 fail-closed 语义正确，应保留。
3. **需容忍时钟偏移**：内网 NTP 常年不准，过期校验应保留容差，否则出现随机鉴权失败。
4. **受众支持多值**。
5. **未映射角色不得授予任何权限**（默认拒绝），现有行为正确。
6. **撤销语义**：JWT 无状态。当前采用短 TTL 加复核的方式，边界标注诚实；对金融与医疗类客户应补充令牌内省。
7. **SAML 不要手写**，使用成熟库；自行解析 XML 签名会引入安全漏洞。

### 4.5 改动落点

| 文件 | 改动 |
| --- | --- |
| `kernel/ports.py` | 扩展身份 Port，增加能力声明方法供 Resolver 选择 |
| `services/identity.py` | 单后端改为注册表加分派器；凭据改为有 schema 的类型 |
| `apps/composition.py` | 硬编码装配改为按配置装载通道列表 |
| `adapters/identity/oidc.py` | 移除专有假设，改为读配置；并接入组合根 |

### 4.6 与执行循环集成的交叉点

认证始终由 AgentOS 网关层负责，外部执行框架不参与身份判定，也不得绕过认证直接派发。

但两者有一处必须协同：**会话归属必须绑定租户标识**。采用外部执行循环后，会话可在多次调用间保持，若不绑定租户，存在跨租户复用会话的风险。此约束应在接入执行循环时一并落地，不能留到事后补。

## 5. 模型路由与成本计量

| 组件 | 规模 | 建议 |
| --- | --- | --- |
| `services/model_router.py` | 125 行 | 降级链与能力协商改用 LiteLLM |
| `services/budget.py` | 34 行 | 成本计量部分可由 LiteLLM 分担；预算闸门保留自研 |

LiteLLM 为 MIT 许可，覆盖 100 多家供应商，内置降级链、虚拟密钥、预算上限、成本归集与可观测导出。

**两条 LiteLLM 不具备、必须留在 AgentOS 外层的能力：**

1. **隐私路由**：按数据分级限制出域（`local_only` 不得出境）。降级链不得扩大数据出域范围。
2. **策略内容**：其护栏只提供钩子，不提供策略。PII 脱敏与提示注入拦截仍是本项目 Policy 的职责。

建议先以 SDK 模式接入，不引入独立代理服务，避免多起一个进程。

## 6. 存储与资产

### 6.1 数据库层

`adapters/store/sqlite.py` 2057 行手写 SQL → 改用 SQLAlchemy Core（非 ORM，保持显式 SQL 控制）+ Alembic 管理迁移。

**必须完整保留的语义**（位于 `kernel/store.py` 与相关领域服务）：

- 租约与 fence 机制，防止重复执行；
- 事件账本；
- 幂等键与稳定幂等语义；
- 不确定态步骤的对账流程；
- 状态机与终态判定。

这是全部改动中**风险最高**的一项，见 §9 前置条件。

### 6.2 资产存储

`services/assets.py` 499 行中的存储部分 → 接入 MinIO / S3 / R2 兼容对象存储。

保留：主体绑定与访问控制、`to_public` 投影（客户端视图不含内部路径）、按内容哈希的稳定资产 ID 与幂等语义。

### 6.3 嵌入

`adapters/embed/ollama.py` 66 行硬绑定单一本地服务 → 抽象为嵌入 Port，可切换为本地句子嵌入库。

保留：摄取与查询必须使用同一嵌入模型，维度指纹记录在元数据中，检索时校验不一致即拒绝。

## 8. 明确保留清单

以下为本项目核心差异化，不替换。记录复审条件以便将来重评。

| 组件 | 保留理由 | 复审条件 |
| --- | --- | --- |
| `kernel/` 全部 | 状态机、Port 边界、决策契约、账本协议构成护城河 | — |
| `services/policy.py`（108 行） | 规模不大且与本项目语义深度耦合；换策略语言需引入新进程与学习成本 | 需要多企业复杂授权模型时评估 OpenFGA 一类关系型授权 |
| `services/approvals.py`（93 行） | 审批指纹与授权绑定是治理核心 | — |
| `services/access.py`（378 行） | 服务端读取资源关系，客户端声明不作为归属证明 | 同上，随 policy 一并复审 |
| `runtime/executor.py` 的闸门 | 模型建议无授权效力，放行由确定性规则裁决 | — |
| `services/knowledge.py`（774 行） | 单机自用场景下全文检索加向量检索加融合排序是合理选择；换独立向量库需起服务，违反默认单机约束 | 需要规模化或独立检索服务时重评 |
| `services/audit.py`（38）、`notify.py`（51） | 规模过小，引入依赖成本高于自维护 | — |
| `adapters/tools/mcp_hub.py`（304 行） | 已基于官方 SDK | — |
| `services/skills.py`（238 行） | 已采用开放的技能文件格式，兼容性良好 | — |
| `apps/gateway.py`（1746 行） | Web 框架本身即成熟开源，无需替换 | — |

关于决策层：`kernel/decision.py` 与 `services/decision_service.py` 被刻意设计为**影子建议层**，默认只写入审计，不得据以放行。**不应将其提升为执行路由**：决策契约只表达选择、评分与是否概率三类题型，无法产出工具调用参数；且将建议层扶正会拆掉本项目相对通用执行框架的结构性优势。

正确用法：决策层留在影子闸门与风险建议位置，积累校准数据；只有当某个具体闸门被证明稳定优于规则时，才将该单一闸门切换为模型，且仍保留确定性兜底。

## 9. 落地顺序与前置条件

按「收益 ÷ 风险」排序：

| 序 | 改动 | 风险 | 前置条件 |
| --- | --- | --- | --- |
| 1 | 可观测 → OpenTelemetry | 极低 | 无 |
| 2 | 定时 → APScheduler | 低 | 无 |
| 3 | 模型路由 → LiteLLM SDK | 低 | 确认隐私路由留在外层 |
| 4 | 身份 → 成熟认证库 + 配置化 | 中 | 先确定 Resolver 匹配规则 |
| 5 | 工具路由 → 复用向量检索 | 低 | 无 |
| 6 | 存储 → SQLAlchemy + Alembic | **高** | **必须先补齐语义回归测试** |
| 7 | 工作流与规划 → Temporal | 中高 | 需先确定与执行循环的上下层关系 |
| 8 | 执行循环 → Codex app-server | 中高 | 需明确状态分家方案 |

**第 6 项的前置条件必须满足**：租约 fence、幂等、不确定态对账这几条语义全部压在手写 SQL 上，换层时极易被静默破坏。先把这些语义的行为测试补到有覆盖，再动实现。

## 10. 红线与元原则

1. **一次只换一个**，不并行推进。
2. **换前先补测试**，尤其是涉及 §6.1 保留语义的改动。
3. **100 行以内的自研件不换**。
4. **不为了用开源而用开源**。目标是降低维护面积与提高正确性，不是提高第三方依赖数量。
5. **语义与实现分离**。凡是替换，Port 契约与上层语义不动，只换底层。
6. **不合并外部状态与治理账本**，用外键关联。
7. 若为公司项目，**优先使用公司内部框架与组件**，其次才是开源方案。

## 11. 待定与未验证

以下事项尚未验证，实施前需确认：

1. 各开源方案在本项目 Python 版本与依赖约束下的兼容性未实测。
2. Codex app-server 的协议版本演进较快，接入前需确认当前版本支持所需方法。
3. 执行循环若保留自研路径，上下文压缩的接入点需另行设计：压缩区间边界只能落在「一整轮助手消息及其全部工具结果」上，否则会破坏工具调用配对校验与审批指纹；触发点应在用量达阈值时主动压缩，而非耗尽后终止。
4. 身份配置的完整字段、默认通道行为与多通道冲突时的裁决规则未定。
5. 本文未评估 `apps/gateway.py`、`services/demo.py`、`services/collaboration.py`、`services/template_runner.py` 的内部重构价值，它们不属于"替换为开源件"的范畴。
6. 相关决策尚未登记为架构决策记录，实施前应按 ADR 流程补记。

## 12. 独立复审与定位调整

用户明确定位为连接企业分散 AI 与既有系统的集成底座，企业额度与项目管理后置。全局遵守提交前隐私脱敏、公司框架优先/其他项目成熟开源优先。本节记录确认前的复审；方案现已实施，进度以 [开发计划](04-开发计划.md) 为准。

本轮独立读取代码，并核对 GitHub 与官方文档，主要裁定如下：

| 原建议 | 复审结果 |
| --- | --- |
| Codex 替代 loop | 同意方向；报告、协作和 PlanRunner 的独立执行路径一并迁移，不能只换 `runtime/loop.py` |
| 上下文压缩与 retain | 使用框架保留后续推理状态；不承诺所有第三方模型支持相同机制。原文数倍收益与排他选型论据缺少可复核基准，不作为本项目结论 |
| 任意自定义兼容端点 | 核对配置为 Responses 协议；不能把 Chat Completions 兼容当等价。模型、工具流和压缩需实测 |
| Runtime/Temporal 状态映射 | 一次 turn 可含多次模型调用，一个流程 run 可含多个 agent thread；按节点关联，分别保存会话、引擎历史与治理账本 |
| 动态工具接治理 | 当前为实验 API；优先稳定 MCP 工具代理并限制原生 shell 的业务访问，SDK/RPC 回调能力先验 |
| Temporal 替代自研流程 | 同意编排/等待/恢复/重试替换；另用 React Flow 做可视化节点编辑。节点定义与业务校验仍是薄集成层 |
| 仅配置身份通道 | 不足。当前 worker/loop 固定 `default`，须修到知识、工具、沙箱、成果、回调和恢复全程归属；身份有效期夹紧到 JWT exp，issuer + sub 稳定映射 |
| LiteLLM SDK 优先 | Codex 内部请求不经过原 Python SDK 调用路径；改为企业网关优先或开源 Proxy，含调用前预算闸门与压缩用量 |
| 先可观测/定时/数据库 | 改为核心集成闭环优先；整体 SQLAlchemy/对象存储迁移后置，不为清单增加基础设施 |
| 少于 100 行一律保留 | 改按风险和总成本判断；协议、安全、密码学与沙箱不能靠行数决定是否自研 |
