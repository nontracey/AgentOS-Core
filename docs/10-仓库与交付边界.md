> 文档性质：源码维护、部署引用与开源边界
> 适用范围：开源核心、独立个人部署与企业集成
> 阅读入口：[文档目录](README.md)

## 1. 一个核心，多种部署

核心仓库维护后端、默认同源 UI、通用治理、契约、测试和通用适配器。个人部署和客户交付各自维护配置、编排、专属适配、业务流程与运维文档，引用同一核心版本，不复制核心源码建立分叉。

| 内容 | 所属仓库 |
| --- | --- |
| Codex / Temporal / MCP / Skill / OIDC / JWT / WeKnora 的通用接入 | 核心 |
| 特定企业旧业务系统、字段和业务权限映射 | 客户集成 |
| 机器分配、个人模型路由、自用流程 | 个人部署 |
| 真实凭据、身份文件、业务数据、日志、现场截图 | 受保护本地存储或企业秘密系统，不进入任何 Git |

多台机器连接一个核心不意味着核心已支持多副本或高可用。公开示例使用合成数据与占位符；部署数量、操作系统和模型提供方由使用者选择。

## 2. 部署方引用核心

开发环境可通过 uv 的本地 path source 引用相邻核心目录，目录位置由部署仓库约定，核心不反向读取它。正式交付使用固定版本的软件包或不可变镜像，并在部署仓库记录版本和来源；企业已有身份、模型网关与业务系统优先复用。

源码首次安装、测试和构建：

```sh
uv sync --frozen
cd frontend/workflow
npm ci
npm run typecheck
npm run build
cd ../..
uv build --wheel
```

构建 wheel 前必须构建工作流编辑器。wheel 使用明确列表携带生产 UI 与内置 Skill，源码安装使用根目录 frontend；不打包前端开发依赖、配置、证据或个人脚本。Docker 多阶段构建生成编辑器，并安装固定版本 Codex。具体运行配置见 [集成部署](09-集成部署.md)；默认 scripted 是验证环境，真实推理仍需配置可用模型。

独立 wheel 安装后可运行 `agentos serve --host 127.0.0.1 --port 8800`。Codex 程序是 wheel 部署的外部依赖，按实际版本和平台安装；模型兼容性需单独验证，不能由包安装成功推断。

## 3. 集成和升级

优先通过 HTTP / MCP 接入外部服务。确实需要同进程扩展时使用既有 Port/Adapter 和组合根，不修改 kernel/runtime 的依赖边界；任意动态插件加载并非当前实现。通用修复回到核心，客户专有规则留在客户仓库。

升级先核对组件和核心版本，在隔离数据中演练恢复与回滚；再切换部署方固定引用。不自动替换已有服务或删除卷。受理中的任务、来源、工作流和 Skill 版本保持绑定，未知效果先对账。

## 4. Git、隐私和交付

核心建立独立本地 Git 历史，不继承部署仓库的历史、远端、身份材料或现场文件。初始 Git 作者采用公开项目身份；第三方许可与必要版权声明保留。新增远端和发布需要另行授权。

提交前检查源码、测试样本、文档、SVG/HTML、图片和包内容；Gitleaks 与人工核对共同使用，不将扫描通过视为绝对无泄露。Git ignore、Docker context 排除和 wheel 的文件清单分别维护；公开资料不依赖部署目录或忽略文件。

当前许可证为 Apache-2.0，正文见 [LICENSE](../LICENSE)，声明见 [NOTICE](../NOTICE)。[组件清单](../contracts/oss-licenses.json) 只覆盖直接依赖和选定组件，不是完整容器/间接依赖合规结论。后续完整 SBOM、镜像发布与目标架构验证由 [开发计划](04-开发计划.md) 记录。

开源核心可由用户自行部署。收费交付应写明接入范围、业务场景、验收、模型费用、升级和维护边界；实际企业身份/旧系统验证不能以合成测试代替。
